# 竞品研究 · Linkly AI → ROM-AI 可借鉴能力分析（2026-07-07）

> 输入:Linkly AI 0.7.0 安装包(`C:\Users\yz_ya\Downloads`,23.6MB)+ 官网 linkly.ai/zh。
> 方法:官网抽取 + 安装器二进制实证(NSIS v3.11 头 / Linkly AI LLC 签名);未安装运行(陌生第三方 exe,与本地隐私命题无关,不装)。
> 结论先行:**ROM-AI 与 Linkly 同栈不同命**——Linkly 是"文档检索供给层(管道)",ROM-AI 是"设计事务所判断工作台"。ROM-AI 不该变成管道,而该把管道的三项强能力**内化**。

## 一、Linkly 是什么(实证)

- **定位**:"为 AI Agents 设计的本地搜索引擎"——把本机文档转成 **AI 可用上下文**。自己不做对话/判断,专门给外部 AI(Claude / 任意 MCP 客户端)当索引与检索后端。

> **更正(2026-07-07,据用户后补的设置页截图):** 上句"自己不做对话"**有误**。Linkly **自带 Chatbot + 对话模型设置**(默认模型/回复语言/模型提供商),并内建嵌入模型 **Qwen3-Embedding-0.6B**(装完自动下载,语义搜索用)。它是"本地检索供给(MCP/CLI) + 自带对话"一体,不是纯管道。此更正同步在 [竞品-Linkly-UI借鉴-数据基地与营地-20260707.md] §〇。**P2 向量选型采信 Qwen3-Embedding-0.6B**(比下文猜的 bge-small 更具体、中文更强)。
- **技术画像**(安装器实证):NSIS v3.11 安装器(= Tauri 官方 Windows 打包器);23.6MB;发行方 Linkly AI LLC。体积+"Rust系/AppImage/5分钟索引/0.5秒查询/~100语言"自述 → **高度疑似 Tauri(Rust + WebView2)**,非 Electron(那类通常 >60MB)。
- **四大能力**:
  1. **文档检索** — 关键词 + 语义模糊 + 跨~100语言。支持 PDF/DOCX/HTML/MD/EPUB/图片OCR。
  2. **大纲索引(杀手锏)** — 每份文档建**分层大纲**,AI"渐进式披露":先看目录→按需展开章节,不一次性灌全文(省 token、提准度)。
  3. **AI 对外供给** — 4 个工具 + **MCP server / CLI / Agent Skills** 三种接入。
  4. **本地隐私 + 极速** — 数据不出本机;后台常驻;全局快捷键唤起;全键盘。

## 二、ROM-AI 现状 vs Linkly(摸过代码,非臆测)

| 能力 | ROM-AI 现状 | Linkly | 判定 |
|---|---|---|---|
| 全文检索 | ✅ FTS5 + **BM25 排序**(retrieval.py) | ✅ | 关键词层已追平 |
| 格式解析 | ✅ PDF/DOCX/PPTX/XLSX/TXT/MD + **图片OCR(RapidOCR 本地)** | PDF/DOCX/HTML/MD/EPUB/图片OCR | 各有缺:ROM-AI 缺 **HTML/EPUB**;Linkly 缺 PPTX/XLSX |
| **语义检索** | ❌ 仅 FTS5 关键词/BM25,无向量 | ✅ 本地向量模型跨100语言 | **真差距①** |
| **大纲索引** | ❌ 无分层大纲/渐进披露 | ✅ | **真差距②** |
| **MCP/CLI 对外** | ❌ 无(仅腾讯会议 provider) | ✅ MCP+CLI+Skills | **真差距③(方向可选)** |
| 对话/研判/会议链路 | ✅ ROM-AI 独有 | ❌ Linkly 无 | ROM-AI 是判断台,Linkly 是管道 |

## 三、可模仿清单(按 ROI 排序,对齐现有代码)

### 🟢 P1 · 大纲索引 + 渐进式披露(最高 ROI,最贴 ROM-AI 命题)
- **是什么**:入库时给每份文档抽**分层大纲**(标题层级 / PDF 书签 / DOCX heading / MD `#`),存为结构化字段;检索/研判时先给 AI 目录,再按段落 ID 取正文。
- **为何最该做**:ROM-AI 研判/会议纪要现在把长文**整篇**塞进 LLM 上下文(token 贵、易超窗、召回噪声大)。大纲索引让"研判引用某段"精确到章节 → 省 token + 出处更准(接上现有"段落级溯源 P6"待办)。
- **落点**:`parsing.py` 抽大纲(fitz 的 `get_toc()` 已现成拿 PDF 书签;docx heading;md 正则)→ 存 `knowledge_documents.outline`(新 JSON 字段)→ `retrieval.py` 加"按大纲节点取正文"接口 → 研判/会议 RAG 消费。
- **不做**:不引入外部服务;纯本地结构抽取,零新依赖(fitz/python-docx 已在)。

### 🟡 P2 · 本地语义检索(向量)作为 FTS5 的补充召回
- **是什么**:本地向量模型(如 bge-small-zh / multilingual-e5-small,~100MB,CPU 可跑)给文档 chunk 建 embedding,查询时向量近邻 + FTS5 BM25 **混合排序**(hybrid),补关键词检索召回不到的"语义相近但用词不同"。
- **为何**:设计事务所资料同义/跨语言多("立项文本"vs"项目建议书"),纯 BM25 漏召回。跨语言是 Linkly 明确强项。
- **落点**:`retrieval.py` 加 `embedding.py`(本地模型,懒加载);FTS5 结果与向量结果 RRF 融合;`/search` 加 `mode=hybrid`。
- **成本/风险**:+1 个本地模型依赖(~100MB,打进包体积涨)、首次索引变慢。**建议先做 P1 看效果,P2 待你评估体积成本后再定**。ROM-AI 现有"半成品向量"痕迹需先核(见待办)。

### 🟡 P2 · 补 HTML / EPUB 解析格式
- **是什么**:`parsing.py` 加 `.html`(BeautifulSoup 抽正文)/`.epub`(ebooklib)两格式,追平 Linkly 覆盖面。
- **为何**:甲方常发网页存档/电子书规范;当前直接 unsupported。
- **落点**:`SUPPORTED_EXTS` 加两项 + 两个抽取分支;走现有五态(ok/metadata_only/empty/...)。低风险、独立可做。

### 🔵 P3 · MCP server 对外供给(战略级,非近期)
- **是什么**:把 ROM-AI 的检索/知识库包成 **MCP server**,让用户的 Claude Desktop / Cursor 直接查 ROM-AI 库——ROM-AI 从"应用"升为"你所有 AI 的记忆后端"。
- **为何缓**:这是**产品定位跃迁**(呼应"认知资产可移植性/上下文供给做成产品功能"那条记忆),不是小功能。需单独立项拍板,不塞进现有迭代。
- **落点**:新 `mcp_server.py`(暴露 search/get_document/get_outline 工具);与桌面 app 同库不同进程。**登记 backlog,不在本轮动**。

## 四、明确不模仿(定位纪律)
- **不把 ROM-AI 变成"纯管道/无头检索器"**:Linkly 无对话无判断是它的克制,ROM-AI 的价值恰在判断层(研判/会议/协作),砍了就成了另一个 Linkly。
- **不追"全局快捷键唤起/后台常驻搜索框"**:那是 Linkly 作为系统级工具的形态,ROM-AI 是工作台形态,不需要。
- **不重造已有**:FTS5/BM25/OCR/PDF-DOCX-PPTX-XLSX 解析 ROM-AI 都有,只补差集(HTML/EPUB/大纲/向量)。

## 五、建议执行顺序(待你批)
1. **P1 大纲索引**先做——ROI 最高、零新依赖、直接改善现有研判/会议 token 成本与溯源精度。
2. P2 三项(向量 / HTML / EPUB)按你对**包体积**的容忍度取舍:HTML/EPUB 低成本可顺带;向量涨体积需你点头。
3. P3 MCP 单独立项,登记 backlog,呼应"上下文供给产品化"命题。
