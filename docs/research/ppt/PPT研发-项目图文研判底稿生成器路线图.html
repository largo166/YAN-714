ROM-AI · PPT研发 · DeckPlan 图文底稿生成能力

项目图文研判底稿生成器 1.0

这条研发线不是“一键生成最终 PPT”，而是让 ROM-AI 读取项目资料，先生成可审查、可追溯、可替图的 DeckPlan 结构化页面计划，再渲染成可继续深化的图文底稿。

AI 放 60% 自动完成结构、判断、图片槽、候选素材和来源记录。
人工替 40% 设计师负责替图、深化判断、调整版式和主创表达。
DeckPlan 优先 先做 JSON 编排层，再做 PPTX 渲染，不直接冲最终导出。

一、研发定位

定义清楚，避免做成通用 AI PPT 玩具
产品定位

项目启动图文工作台

面向方案前期、投标、概念启动，把零散资料编排成可继续深化的图文底稿。

核心对象

DeckPlan

每页包含判断标题、文本要点、图片槽、候选资产、来源证据和备注依据。

明确不做

不追求全自动终稿

第一版不解决所有图片语义匹配，不做万能模板，不承诺自动排出可汇报终稿。

二、总技术路线

复用现有底座，只新增编排层
1

资料接入

复用项目文件、解析和抽图链路，形成文字、图片、页码、caption。

2

素材盘点

识别有什么、缺什么、哪些材料不可读，建立图片候选池。

3

DeckPlan 编排

生成结构化 JSON：章节、页面判断、图片槽、候选图、来源证据。

4

PPTX 渲染

按 DeckPlan 渲染底稿：有图放图，缺图黑占位，备注写依据。

5

人工替图

前端页列表、候选图池、图片槽替换；MVP 后置。

三、复用与新增边界

先复用，不重造第二套
能力层 必须复用 新增内容 边界说明
资料解析 parsing.py 素材盘点时读取解析状态、页码、分块、截断信息 不重写 PDF/PPTX/DOCX/XLSX/OCR 解析器
图片资产 image_assets.py、FileAsset 图片语义粗分类、候选打分、图片槽推荐 第一版只推荐 2-5 张候选，不追求全自动放准
文件接口 project_files.py 读取项目资料包、资产池、缩略图 URL 不新建独立文件管理系统
研判沉淀 ProjectAnalysis、SkillResult DeckPlan 可先作为技能结果 JSON 或研判结果 JSON 保存 MVP 先不建表，待验证后决定是否持久化为独立对象
PPT 渲染 exporters.build_pptx() 支持图片槽、黑占位、页脚来源、备注依据 渲染层是第三阶段，不是第一阶段

四、DeckPlan Schema 草案

PPT研发的核心资产，不是 PPTX 文件
结构原则

页面计划必须可审查、可替换、可追溯

  • Deck 级记录项目名、汇报类型、模板、章节。
  • Slide 级标题必须是具体判断，不允许空壳标题。
  • 图片槽是一等对象，记录类型、是否必需、候选图和 fallback。
  • 来源证据指向 PDF 页码、PPT 页码、FileAsset、文本片段。
  • 备注区记录判断依据，供人工复核和深化。

五、四阶段研发过程

先大纲规划，后代码落地；P0 检索完成后单独排期
阶段 1素材盘点
目标
  • 抽文字、抽图、缩略图、页码和 caption。
  • 输出“有什么 / 无法读 / 缺什么”。
技术节点
  • 复用 parsing.py、image_assets.py。
  • 形成素材盘点 JSON，不调用 PPT 渲染。
成果标准
  • 能列出项目文字材料、图片资产、不可读文件。
  • 每张候选图有来源文件、页码或 caption。
阶段 2DeckPlan 编排
目标
  • 生成 8-12 页结构化 JSON。
  • 每页带判断、图片槽、候选图和来源证据。
技术节点
  • 新增 DeckPlan schema 与生成 prompt。
  • 先支持“前期研判 Deck”和“设计策略 Deck”。
成果标准
  • JSON 可被人工审阅和修改。
  • 标题没有“项目分析/区位分析”这类空壳词。
阶段 3PPTX 渲染
目标
  • 把 DeckPlan 渲染为可编辑 .pptx。
  • 支持图片槽、黑占位、页脚来源、备注依据。
技术节点
  • 升级 exporters.build_pptx()。
  • 图片不确定时放候选提示，不强行放错。
成果标准
  • 导出的 PPTX 可继续编辑。
  • 缺图页明确写出需要哪类图片。
阶段 4人工替图界面
目标
  • 提供页列表、预览、候选图池和拖图替换。
  • 让人工 40% 变成顺手的编辑流程。
技术节点
  • 前端读取 DeckPlan 和 FileAsset 缩略图。
  • 保存替图后的 DeckPlan 再渲染。
成果标准
  • 设计师能在页面内替换图片槽。
  • MVP 后置，不抢阶段 1-2。

六、MVP 页面清单

先做两套模板，每套 8-12 页，不做 30 页大而全
模板 A

前期研判 Deck

1. 封面判断项目一句话机会，而非普通封面。
2. 资料盘点已有材料、缺失材料、不可读材料。
3. 区位机会城市关系带来的具体设计机会。
4. 场地约束红线、交通、景观、界面矛盾。
5. 人群与需求使用者或甲方诉求的关键转译。
6. 竞品空白同类方案都在做什么，本项目避开什么。
7. 机会命题最值得主创推进的 2-3 个问题。
8. 下一步资料清单缺哪些图、哪些数据、哪些判断。
模板 B

设计策略 Deck

1. 主概念一句话 main idea + 概念图槽。
2. 场地回应概念如何来自场地，而非套话。
3. 空间策略入口、序列、核心空间、高潮。
4. 体量策略形体动作与指标/界面关系。
5. 立面策略材料、光影、比例、识别度。
6. 体验场景人视、到达、活动、灰空间。
7. 标杆转译借鉴底层逻辑，不模仿符号。
8. 风险与补图最弱逻辑、缺图项、人工深化动作。

七、三条红线的落地方式

决定这个能力是否专业，而不是玩具
红线 1

图片槽是一等对象

  • 每页必须声明所需图片类型。
  • 匹配不确定时推荐候选，不强行确定。
  • 缺图时生成黑占位和明确缺图说明。
红线 2

来源可追溯

  • 每页记录文本来源和图像来源。
  • 来源包含文件、页码、资产 ID、caption。
  • PPT 页脚和备注区保留依据。
红线 3

判断不空泛

  • 页标题必须是判断句。
  • 禁止“项目分析/区位分析/设计理念”。
  • 每页必须回答“所以呢”。

八、成果标准

用可验收标准防止范围膨胀
DeckPlan 可读产品、设计师、开发都能直接审阅 JSON，知道每页想表达什么。
页面有判断8-12 页中 90% 以上标题为具体判断句，不是栏目名。
图片槽可替每个图片槽都有类型、需求说明、候选图或黑占位。
来源能追每页至少有一条可回查来源；图片能回到 FileAsset 或源文件页码。
缺失诚实缺图、不可读、材料不足必须显式说明，不用 AI 编造。
PPT 可深化导出的 PPTX 是底稿，设计师能继续替图、改字、调版。

九、研发优先级与风险

这是一条大线，不与 P0 检索抢工
优先级 事项 判断 处理方式
P0 后启动 DeckPlan 大纲规划 现在可先出规划，不写代码 确认 schema、阶段、验收标准后再排研发
MVP 核心 素材盘点 + DeckPlan JSON 价值在中间层，不在 PPT 导出 阶段 1-2 优先，阶段 3 延后
高风险 图片语义匹配 第一版很难全自动准确 只做候选推荐 + 人工替换
高风险 版式稳定 自动排版容易拼贴感强 固定两套模板，限制页面类型
高风险 判断空泛 通用 AI 容易生成漂亮废话 标题校验 + 来源约束 + “所以呢”检查
一句话口径： PPT研发不是 PPT 导出功能，而是 DeckPlan 驱动的项目图文研判底稿能力；AI 先搭结构和证据骨架，人工再替图深化。
