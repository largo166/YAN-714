# ROM-AI 开发环境进程拓扑

> 立于 2026-07-06(端口误杀事故后)。**变更即更新铁律**:凡改动进程结构(加 TTS 容器/换托管方式/改端口),此图随 commit 同步更新——过期的拓扑图比没有更危险,它给错误操作提供错误的信心。

## 一、进程清单

| 进程 | 启动命令 | 由谁拉起 | 端口 | 实测 PID 示例 |
|---|---|---|---|---|
| 后端 uvicorn | `.venv/Scripts/python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000`（cwd=backend） | **launch.json → preview 托管** | 8000 | 35900 |
| 前端 vite | `npm run dev`（cwd=frontend） | **launch.json → preview 托管** | 5173 | 36560 |
| 原型静态服 | `python -m http.server 4599`（cwd=prototypes） | launch.json → preview 托管 | 4599 | 29104(可有可无) |

> 唯一起服方式 = **preview_start + launch.json**。不再手工在终端 `npm run dev` / `uvicorn` 拉起——手工拉起会脱离 preview 托管,且落进某个 shell 会话/进程组,是这次误杀连坐的根因。

## 二、父子关系(核心 —— 这次教训欠在这一行)

```
后端链:  [preview 托管进程]
            └─ python.exe (uvicorn reloader, PID 55184)      ← --reload 的监视父进程
                 └─ python.exe (uvicorn worker, PID 35900) ← 真正 LISTENING 8000

前端链:  [preview 托管进程]
            └─ cmd.exe / npm wrapper (PID 46072)
                 └─ node.exe (vite, PID 36560)             ← 真正 LISTENING 5173

两条链彼此独立,无共同祖先。
```

**杀谁连坐谁**:
- 杀 uvicorn reloader 父(55184)→ worker(35900)一起死,8000 断。
- 杀 vite 的 npm/cmd wrapper（46072）→ vite(36560)一起死,5173 断。
- **反面教训(本次事故)**:上次手工 `npm run dev` 起的前端(PID 45500)与后端处于关联会话,停前端时波及了后端 → 8000 意外掉线。虽然 preview 托管后两链已独立,但 **uvicorn 的 reloader/worker、vite 的 shell wrapper 这类"隐藏父子"依然存在**——任何 kill 前必须先查进程树。

## 三、端口契约

| 端口 | 锁死? | 为什么 |
|---|---|---|
| **8000** | **锁死** | ① backend `main.py` 同源托管 dist ② CORS 白名单认这个源 ③ 生产 exe 用它。换端口断前后端链路。 |
| **5173** | **锁死** | ① vite.config `strictPort:true`(端口占用即报错退出,不悄悄换) ② 开发态前端拉 `http://127.0.0.1:8000` 是同源约定 ③ preview_eval 验证都指向它。 |
| 4599 | 无所谓 | 原型静态服,仅历史原型预览用,可换可停,不影响 ROM-AI 本体。 |

`launch.json` 已对 backend/frontend/prototypes 全部设 **`autoPort:false`**,声明"端口固定"的意图。

## 四、启停顺序

**开机序列**（正确）:
1. `preview_start` name=**backend**（等 uvicorn ready:轮询 `/api/projects` 到 200,冷启约 2-6s,要加载 DB/技能注册）
2. `preview_start` name=**frontend**（vite 秒起）
3. 浏览器开 `http://127.0.0.1:5173/`

> 顺序原因:前端起来就会拉后端数据;后端先 ready 可避免首屏一片加载失败。反过来也能跑(前端会重试),但先后端更干净。

**关机序列**:先停前端再停后端(反序);或直接 `preview_stop` 各自 serverId。

**只重启前端**（改了 seasky 代码、HMR 没吃干净时):
- `preview_stop <前端 serverId>` → `preview_start frontend`。**后端不动**,链路自动恢复。

**只重启后端**（改了 backend 代码 / 后端假死):
- `preview_stop <后端 serverId>` → `preview_start backend` → 等 200。**前端不动**,它会自动重连。
- ⚠️ 重启后端前先做本文档 §五 的中断排查(有无进行中的收件箱扫描/索引)。

## 五、后端死亡时的中断作业排查（每次重启后端必做）

后端(收件箱)有 **60s 后台轮询扫描**(`desktop/launcher.py` / inbox 线程),会持续入库。后端被杀时可能打断半截扫描。排查:
1. `GET /api/inbox/status` 看 `pending`(待处理数);
2. `GET /api/knowledge/stats` 看 `documents`/`indexed`;
3. 与上次记录比对增量是否连续(2026-07-06 实测:pending 355→358、docs 640→643,增量一致 = 扫描连续无丢失)。

**收件箱扫描是幂等的**(同名同大小去重,原件在 `_done/`),中断后**下一轮 60s 自动续扫,无需手工重触发**;真需要立刻补扫用 `POST /api/inbox/scan`,**不静默重跑**。索引失败的单文件计数呈现、不致命。

## 六、操作铁律（不可降级）

> **杀任何进程前,必须先查其进程树,确认没有关键子进程会连坐。**
> Windows 查法:`netstat -ano | grep LISTENING` 找端口 PID → `Get-CimInstance Win32_Process -Filter "ProcessId=<pid>"` 看 ParentProcessId,逐级追。uvicorn 有 reloader→worker 两层,vite 有 shell wrapper 一层,都属"隐藏父子"。
> 起服只走 `preview_start` + launch.json,**禁止手工终端拉起**(脱离托管 + 会话组连坐风险)。
