# 命名建议 · 营地技能 judge 语义冲突三方案（2026-07-08 · 只建议不迁移,等盲评后统一定）

> **【已裁决:搁置(2026-07-08)】** C-P1 不建(盲评裸问3:0),命名迁移随之搁置——judge 保持现语义"节点督办"不动,不迁移历史 skill_results、不 dry-run、不批量替换。若未来锻造链经复测复活,用户倾向为:保守处理(现有督办不动,锻造链内部另起命名空间,即方案A/C 的组合方向)。

> 冲突现状(代码实证):营地技能注册表里 `id=judge` 是**"节点督办"**(skills.py:62 "盯紧里程碑与逾期风险";prompt=skills.py:88 梳理节点挑风险)——督办属驾驶舱/协作语义。而锻造链方案里 judge 是**"平庸刺客"**(杀候选概念)。同一 id 两个灵魂。
> 本文只给 3 套命名方案,**不迁移、不重命名、不改现有技能**。

## 现状盘点(改名的影响面,先摸清)
- `judge` 出现处:`skills.py` 注册表+prompt 表;旧 CampPage AGENTS 卡(已退役);无独立表字段绑定(skill_results.skill_id 存字符串,历史成果记录里已有 `judge` 值)。
- **改 id 的代价**:历史 skill_results 里 `skill_id='judge'` 的旧成果会与新语义错位(展示时标题对不上)——任何迁移方案都要处理这一点(展示层按 `id+时间` 或 `id+版本` 解析,或数据迁移改写历史值)。

## 方案A · 保守迁移(动最小,先到先得)
- **现有 `judge`(节点督办)保名不动**;锻造链的"平庸刺客"用**新 id `slayer`**(或 `sharpen-judge`)。
- 优点:零历史数据处理、零现有功能改动;锻造链反正是新功能,新 id 天然干净。
- 缺点:锻造链四工序对外叙事是 compete→concept→judge→writer(sharpness 分析文档口径),对外文案与内部 id 不一致,长期认知摩擦。
- 适合:想快、想稳、近期不碰营地存量。

## 方案B · 中性迁移(各归其位,语义中性词)
- 现有 `judge` → 改 id **`chase`**(节点督办/催办,语义自明);锻造链刺客 → 用 **`judge`**(名归锻造链)。
- 历史数据处理:一次性迁移脚本把 skill_results 里 `skill_id='judge'` 改写为 `'chase'`(软处理,dry-run 先过目——数据操作铁律流程)。
- 优点:两个语义各得其名,对外叙事与内部 id 一致;督办改名后还顺势解决"督办放营地本就错位"的问题(chase 可后续平移到协作语境)。
- 缺点:要动一次历史数据(量小:skill_results 里 judge 记录数待查,预估个位数~十位数)。
- 适合:愿意做一次小手术换长期干净。

## 方案C · 强语义迁移(借势改版,四工序全链命名体系)
- 锻造链四工序统一强语义命名:**`redsea`(测红海,替 compete 的链内角色)/ `tension`(锁张力逼非共识,替 concept 链内角色)/ `slay`(杀平庸)/ `forge-writer`(验独占)**;原 22 技能里的 `compete/concept/judge/writer` **保留原名原语义**(单发问答模式继续可用),链与技能是两套 id 空间(链工序 id 前缀 `forge.`)。
- 现有 `judge`(督办)照旧不动或按 B 改 `chase`(可并行决策)。
- 优点:链与技能解耦最彻底——锻造链工序不是"技能的组合",是独立工序(这也符合 C-P1 机制草案的两表设计,forge_steps.step 本就是链自己的枚举);未来技能库怎么变都不影响链。
- 缺点:对外要解释"链工序≠技能"两层概念;命名体系最重。
- 适合:认定锻造链是营地新主线、愿意给它独立命名空间。

## 建议倾向(供参考,你定)
**C 的"链工序独立 id 空间"+ B 的"督办改 chase"组合**:链的四工序在 forge_steps.step 里本来就是独立枚举(C-P1 草案已如此设计),不占技能 id;督办择机改 chase 并移语境。但这是两步棋,C-P0 盲评结果出来后一并定即可。
