# 复盘 · 对着死库做手术（2026-07-07）

> 类别:postmortem。教训已升为 CLAUDE.md 数据操作铁律第 0 条。

## 一句话
存量清洗推进到"去重"时,用真 SHA 复核才发现:开发库 `backend/data/rom_ai.db` 的 870 条 ProjectFile
**物理文件已全部脱节**(storage_root=`c:\仓库`/`c:\仓库-00`,当前开发机磁盘上已不存在),
差一点就在一个"元数据还在、物理文件早丢"的死库上执行了 530 条软删 + 改名 + 删项目。

## 怎么发现的
- 去重口径本想用"同名+同哈希",但库无 content_hash 字段(0023 未做),退用"同名归一+size"。
- 为消除 size 口径误删风险,加 SHA 复核 dry-run → 530 个"副本"SHA **一个都算不出**,
  路径解析全 False → 探测 storage_root 才发现物理文件根本不在盘上。

## 根因
- 这库是**开发/测试期长期积累的历史元数据**:多轮入库测试把记录写进 DB,但物理文件落在
  `c:\仓库`(某次配置)、后改 `c:\仓库-00`(见 storage_root 两值并存),原目录被删/换机 → 文件丢,记录留。
- 测试残留从未清理 → 累积成"假存量",被误当成"真实在用的库需要清洗"。

### 更正(重置后查证):物理文件不是"全丢",是分两批
- storage_root=`c:\仓库`/`c:\仓库-00`(**绝对路径**)的那批 → 换根/换机后**丢了**(SHA 复核 530 副本全算不出即此因)。
- storage_root=`''`(**空,回退 uploads**)的那批 → 其实还在 `backend/data/uploads/{project_id}/`,随开发库走。
- 教训不变:**在做数据操作前必须验物理文件完整**——但要用「storage_root 拼 stored_path」的**真实落盘口径**验,别用臆想路径(我第一次校验就拼错 base,误报"全丢",差点又下错结论)。校验口径本身也要对。

## 差点酿成的错
- 在死库上做清洗 = 清一堆指向不存在文件的记录,**清完也不是任何真实用户会看到的库**——
  "看着努力但无价值",踩"不做无价值内容"红线。
- 且 530 条软删无 SHA 兜底,若目标是真库,size 口径误判不可复核。

## 纠正
1. 数据操作铁律第 0 条(见 CLAUDE.md):**任何数据操作前,先验证目标库是真实在用的库 + 物理文件完整**,排在"脚本先过我"之前。
2. 开发库重置:整库归档(连 storage_root 配置快照)→ 重置干净库 → 可复现种子脚本,测试残留不再累积成假存量。
3. cleanup_stock.py **封存待用**(不作废)——真正目标是用户机器上真实在用的库;等完整性校验功能做出,先对真库跑三态体检(记录在文件在/记录在文件丢/文件在记录无),体检干净再按已批口径清洗。
