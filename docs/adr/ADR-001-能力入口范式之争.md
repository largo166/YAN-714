# ADR-001 · 能力入口范式之争

> 状态:**已定案**(2026-07-06 用户三问批复)
> 决策者:用户拍板;论证由 Fable 5 主控的多视角工作流(3路审计→3立场辩论→红队攻击)产出。
> 命题来源:《共创营地 Composer 设计思考大纲》——"当 ROM-AI 承载 20+ 能力时,用户到底应该如何『交代事情』?"
> 一句话:**composer 不做静默 NL 能力总线;采『显式命令面板』作为能力总线的确认基座——归拢由用户一键点选完成,机器永不替用户猜意图并静默执行。**

---

## 1. 背景与命题

b2 共创营地的 composer 表面是输入框微调(高度/placeholder/发送/模型/接入),实则暴露一个产品级命题:20+ 能力散在五板块时,用户如何用**一种方式**交代所有事情?大纲给出三种 composer 身份供选:①普通输入框 ②技能启动器 ③能力总线(意图→参数→执行→成果→追问统一生命周期)。

**约束(用户红线,不可谈判)**:不假按钮 / 只做确定的 / 最小改动 / 一写新管线就停(NLU 意图路由=新管线需拍板) / 花钱破坏动作显式确认 / 三态诚实。b2 是视觉冻结区,构图不许倒退。

## 2. 决定交互形态的地面真相(审计结论)

- **后端零意图路由/NLU**:`/command` 仅 `text.startswith('/')` + 9 条硬编码字典(`skills.py:_COMMANDS`);营地自由文本**恒发 judge 一个技能**(不自分流);chat 是普通 RAG 不做分发。即"系统识别任务"这一步当前**不存在**。
- **能力总数量级**:后端 ≈120 端点 / 可感能力 ≈50;能被一句意图触发的生成·动作·即答约 **25-30**(22 内置技能 + 9 斜杠别名 + 2 可用 agent + 会议链 + 研判 + 评审 + 生图 + 广播 + 检索类)。
- **"一能力一家"骨架在已发版产品里已是假命题**:检索/纪要/清理三者 `also_in_camp=true`,早已各有两个家。
- **glance 仪表盘**:b1 巨号记忆账本、b0 16 节点带、b4 大盘,是"开门第一眼"的被动扫视视图,进对话流即降维成"一次一问"。

## 3. 三个被否方案(一级知识资产:错误答案比正确答案更值钱)

### 方案 A · 留原地派 —— composer=技能启动器 / 小修波
- **主张**:四能力各守语义家(读取/清理归 b1、建会/纪要归 b0),composer 只做技能启动器;"底座/工作台/共创台"分工是心智骨架。
- **否决理由(红队)**:**答非所问**。命题问"20+ 能力如何交代",它的答案是"记住哪事归哪板"——正是命题在质疑的 O(N) 空间检索负担。它要守护的"干净地图"在已发版产品里就不存在(三能力早已两个家)。且它把 composer 定为技能启动器,"浏览全部技能"就是 22×5 的货架浮层——**没逃出按钮墓地,只是把墓地搬进浮层**。对工程量诚实,对命题不诚实。

### 方案 B · 全归拢派 —— composer=能力总线 / 能力总线波
- **主张**:一切办事从营地一句话触发,b0/b1 退化为成果归档视图;号称"归拢是删重复入口,不是造新管线"。
- **否决理由(红队)**:**承重论点自相矛盾且被代码证伪**。删掉 b1 清理入口并不会凭空产生"一句话触发清理"——真正的总线体验仍需那个不存在的 NLU 路由。它否认自己需要的东西。真做总线要新建三样:①25-30 意图的 NLU 路由(踩"一写新管线就停");②按能力的参数 schema 与生命周期框架(SkillRunIn 只有单一自由文本、无参数 schema、追问线程化基本缺失=新子系统);③掏空 b0/b1 的 glance 仪表盘。**安全面致命**:概率路由静默触发建会/清理/计费=在花钱/删库上"静默做错事",违反不假按钮/三态诚实。重写级 + 跨红线级,灾难性违反最小改动。

### 方案 C · 联邦制派 —— composer=能力总线但限域 / 1.5 波
- **主张**:检索/生成型(读取查询/纪要/复盘)归拢进 composer;破坏/权威动作(清理/建会)双入口并存;仪表盘留板。
- **否决理由(红队)**:**"1.5 波"是掩盖双峰现实的舒适平均值**。把自由文本路由到 22 技能里正确那个(FTS?judge?纪要?MoA?)本身就是 NLU 分类器——与全归拢同一头怪兽,只是限域。于是 either/or:(a)为子集建 NL 路由=踩红线,那它不是 1.5 波而是总线级减仪表盘;(b)靠点选卡片分发(无 NL)=那它根本不是能力总线,约等于小修+改名。"1.5"把这道 either/or 藏了起来。其次它的分界线"带记忆的委托 vs 破坏/权威动作"是按**能力性质**(设计者本体论)划,不是按**用户目标**划:用户说"把上周的会办一下并出纪要"不会把建会体验为"权威动作双入口"、把纪要体验为"委托归拢"——一个用户意图被劈到两条互斥规则,"建会到底在营地还是项目中心"成为它自己承认的高频困惑。

## 4. 决策:第四路 · 显式命令面板(command palette)

三方共同的概念错误:**把"单一入口"错当成"NL 理解"**。命题要的是"一个可靠、齐全的地方够到全部 25-30 项能力"——这不需要机器懂话,只需 composer 的 `/`、`+`、`@` 弹出**显式、带参数、可点选**的面板,消歧由用户一键点选完成。

参照系:Linear / Slack / Notion / Raycast / VS Code Ctrl-P。本质是已发版的 `/command` 系统被提升为一等公民面板。

**同时满足全部约束**:
- 解命题:O(1) 入口,开口即够到全部能力,不用记板位;
- 零 NLU、零新管线:分发用现成 `startswith('/')` + 字典,UI 从 9 条升面板、能力扩到 ~25(`/出图` 花钱确认现成);
- 不倒退仪表盘:面板是叠加加速器,b0/b1 glance 视图原样留板;
- 不动 b2 冻结构图:composer 仍是 composer,面板只是 `/` 触发的浮层;
- 无误路由事故:显式点选=不会静默做错,花钱/删库仍走各自确认闸;
- 不是按钮墓地:输入即筛(type-to-filter),不是浏览货架。

## 5. 架构约束(优先级同"不假按钮",不可降级)

> **命令面板是能力总线的『确认基座』,不是它的替代品。**
> 未来任何自然语言路由,只允许产出"**预填面板项 + 用户一键确认**",**永不静默执行**。
> 尤其在改变世界(建会/清理/写库)与花钱(计费生成)的动作上,机器可以猜、可以预填,但**决定权永远在用户的那一次点击**。

这条约束把"能力总线"从"机器替你做"重定义为"机器帮你够到、你拍板做",既保留 AI OS 的委托愿景,又根除静默误执行的安全事故面。

## 6. 四个能力的去留(基于第四路)

| 能力 | 裁决 | 理由 |
|---|---|---|
| 数据基地读取 | glance 留 b1 + 全文检索作 `/检索` 进面板 | 账本是"一眼全局"被动扫视;检索与 b1 原生入口**同后端端点、无真源分裂** |
| 数据基地清理 | **权威面留 b1;营地卡收回独立执行权,改深链 b1 跳板** | 破坏动作要专属确认场景,不在对话气泡稀释;消除"无项目上下文清理卡混进项目态对话流"的最刺眼串台 |
| 项目中心建会 | b0 tile 留权威入口;面板加 `/建会`(仿 `/出图` 外呼前确认) | 不搬走 |
| 项目中心纪要 | 生成链归面板一站;b0 `listMeetings` 留复盘归档 | 花钱走既有 404 显式确认 |

## 7. 后果与出波

- **本波(小修偏中)**:命令面板 + placeholder 诚实化 + 快捷卡改预填注入 + 清理卡收回执行权 + composer 可靠化。不建意图路由、不建 schema 驱动生命周期、不掏空 b0/b1。技能 schema 仅作面板数据源。
- **明确出波**:①b1 清理浮层升级为"仓库/选取/执行"三步向导(含建仓库、回写全局配置)——先审计后作独立半波;②长任务收起并行——Phase 2 再议。
- **正向后果**:AI OS 的委托愿景保留(面板即"够到一切"),安全边界前移(点选=不静默),b2 冻结区与 b0/b1 身份都不倒退。
- **负向后果/代价**:面板不是"真懂话",用户仍需一次点选(但这正是安全的代价,且 type-to-filter 成本极低);技能扩到 ~25 项时面板需分组/常用置顶以防新的浏览负担。
