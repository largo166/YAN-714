## 一、架构怎么配合这次演进(不破坏现有红线)
这次反馈把 ROM-AI 的定位钉死为「**建筑设计公司的 AI 生产系统**」,不是问答工具。架构主线「知识库为中枢的闭环」完全吻合,但要补**三个横切能力**:

1. **任务/状态层**(新)。当前 `TeamAssignment` 是"静态分工",缺 `status` 流转(待办→进行中→已完成)+过期提醒。这是会议闭环、跨会议追踪、风险提醒的共同底座。→ 加 `status`/`source`(来源纪要id)/`done_at` 字段 + 状态端点。
2. **知识条目模板层**(新)。当前知识库是"文档+元数据",缺"**结构化知识条目**"(决策背景/方案演变/失败教训/可复用经验/设计哲学锚点)。这是"沉淀好的设计"的载体,区别于普通文档。→ 复用 `ProjectCognition` 的受控字段范式,新增"知识条目"module 或独立轻表。
3. **画像/资产聚合视图**(新,大多是查询+前端)。甲方画像、提示词库、材料库、评审清单——本质都是"**按某个维度(甲方/场景/材料)横切聚合已有数据**"。多数不需要新表,是聚合端点+前端卡片。

**不动的红线**:仍 SQLite/本地/单用户;物业全生命周期(场景六)、向量检索仍后置留接缝;不为这些扩服务器化。

## 二、点亮顺序(对齐清单四梯队,但按"已有底座"重排)
清单的 P0→P3 价值排序我认同。但按"离通电最近"微调,让每步都能快速验收:

### 🔴 P0(本周):闭环优先,都在已有底座上点亮
- **A. 会议纪要→任务看板闭环**。`TeamAssignment` 加 `status/source_minute_id/done_at`(Alembic 0017)→ 纪要确认时把 `todos_json` 落成 assignment → 协作平台/项目中心出**任务看板**(待办/进行中/已完成 + 过期标红)。验收:上传妙记→纪要→任务卡片→看板可流转。
- **B. 设计知识库沉淀 v0.1**。定"知识条目模板"(4 维:决策背景/方案演变/失败教训/可复用经验)→ 研判/已确认认知**一键沉淀**成条目(复用 reflow 范式)→ 数据基地可浏览/搜索/关联。验收:市庄项目一条完整知识条目可查可搜。

### 🟡 P1(下周):建能力,靠 P0 的条目层
- **C. 方案评审预检**:评审检查清单模板 + 提交前自动跑 `skills.review` 出"N项通过/M项需关注"。
- **D. 甲方画像库**:甲方为键聚合(诉求/红线/历史项目/黑话)→ 输入"保利"出画像 + 汇报建议口径。
- **E. 汇报文本分口径**:PPT/研判 prompt 加"汇报对象"档(甲方/高层/专家会)。

### 🟢 P2(下月):建资产,从归档里提炼
- **F. 效果图提示词库**:从 `SkillResult` 生图归档按场景分类,沉淀可复用提示词。
- **G. 跨会议议题追踪**:同项目多会议时间线(靠 P0 的 source 链)。
- **H. 项目复盘模板**:四维度自动聚合。

### ⚪ P3(远期留接缝):材料库 / 全生命周期(场景六,物业)——不在本地优先范围内,留接缝。

## 三、与现有工程的衔接(避免重复/冲突)
- 任务看板复用 `team`/`TeamAssignment`,不新建并行系统。
- 知识条目优先复用 `ProjectCognition` 受控字段范式或 `cross_project.precipitate`,不另起一套。
- 沉淀入口复用 `reflow` 的幂等链(reflowed_doc_id),防同名碰撞静默丢。
- 一切判断类输出仍走 RAG+不伪造红线。
- exe 分发(onedir+数据备份+WebView2)是**并行的工程线**,不阻塞功能点亮;但发给设计院前要做完。
