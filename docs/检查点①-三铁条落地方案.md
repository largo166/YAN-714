## 零·B、DeepSeek 参与边界（全局约束，管着三条铁条 + 后续环节）

用户拍板：清理流程里 DeepSeek 的介入范围严格限定，写死如下。

### B1 · 五段流水线一律不调 DeepSeek
识别→抽取→切块→索引→归档，全部是**纯机械确定性操作**（parse_file / content_chunks_json / retrieval.index_one / _extract_and_store_assets，无一涉及 LLM）。
- **理由**：大模型进来会让 SSE 进度、断点续跑、大文件降级这些可控性保证打折，又慢又贵又不稳。
- **约束**：ingest 编排器（S4）内**禁止**任何 DeepSeek 调用。五段的每一步都必须是可预测耗时、可断点、可重试的确定性动作。

### B2 · DeepSeek 介入点 = 归档完成之后，作为独立环节
链路：**入库归档完成 → 自动排一次解析队列 → 后台跑 DeepSeek 生成 16 域研判 → 结果落 `ProjectAnalysis` → 项目中心「分析摘要」有真内容**。
- **复用现成（不新造）**：`analyze` 端点（project_analysis.py:56）已有 `force` 参数——`force=False` 读缓存(62-74行)、`force=True` 强刷；研判生成链 `analysis.py`/`structured_judgment.py`/`llm.py` 现成；结果落 `ProjectAnalysis` 表，b0 摘要读 `latest_analyses`（已验数据不串时读的就是它）。
- **本轮唯一新增**：ingest 编排器末尾挂一个**触发钩子**——五段全部归档后，对该项目排队调一次现有 analyze。**这是编排钩子，不是新造研判**。
- **触发策略**：新项目自动排队解析一次 → 之后读缓存 → 可手动 force 刷新（沿用 analyze 的 force 语义，零改动）。
- **独立于五段**：研判是归档**之后**的独立异步环节，跑不跑、跑多久，都不影响五段的 SSE 进度与续跑判定（五段回执在归档完成即出，研判在其后台进行）。

### B3 · staging 文件分类 = 规则优先，本轮不引入 DeepSeek
铁条2 的 staging 分类用**文件名 + 类型规则**（复用 `parsing.is_supported` + 现有 `classify_by_name` 范式），本轮**不引入 DeepSeek 智能分类**。
- **将来增强（非本轮）**：若真发现规则判不准的边缘文件多，再加"大模型兜底"作**可选增强**，且铁律=**规则优先**、绝不让每个文件都过大模型（只对规则判不出的少数走兜底）。

> 一句话边界：**五段纯机械零 LLM；DeepSeek 只在归档后跑研判（复用 analyze，不新造）；分类规则优先不过模型。**
