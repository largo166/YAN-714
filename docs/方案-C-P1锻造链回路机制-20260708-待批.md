## 一、回路状态机

```
                    ┌──────────────────────────────────────┐
                    │              (打回,带失败原因)          │
                    ▼                                      │
[idle] → ①compete → ②concept → ③judge ─┬→ ④writer ─┬→ [passed 通过]
           红海      张力/候选    处决    │    独占句    │
                                        │             └→ [rejected 打回]──┘
                                        └→ [wiped 全灭]──→ ②concept(带全灭死因重逼)
                                                             │ (全灭重逼仍全灭)
                                                             ▼
                                                        [exhausted 弹尽]
```

**状态集(chain 级):** `idle → running → passed | exhausted | aborted(人工中止/预算触顶)`
**工位状态(step 级):** `pending → running → ok | failed`;打回时下游工位标 `stale`。

**回路规则:**
1. ①红海**每链只跑一次**(红海不随重逼变化,重复跑=烧钱无信息增量)。
2. **writer 打回 → 回②**:concept 带着「writer 失败原因 + judge 幸存者 + 已否决候选清单」重逼(否决清单防复活——裁决落档纪律在链里的镜像)。
3. **judge 全灭 → 回②**:concept 带着「全灭死因逐条」重逼,并被要求换张力来源(不许在同一批张力上换措辞)。
4. 每次回②算**一轮(round)**;新一轮产出走完整 ③→④。

## 二、judge 失败原因结构(结构化 JSON,回路的信息载体)

```json
{
  "verdict": "survived | wiped",
  "survivor": { "main_idea": "…", "sharpen_notes": ["补刀1", "补刀2"] } ,   // survived 时
  "executions": [                                                          // 每个候选一条处决记录
    {
      "candidate": "候选main idea原文",
      "kill_reason": "redsea_collision | weak_tension | self_indulgent",   // 撞红海/张力不实/自嗨(C-P0实测三死因枚举)
      "detail": "撞了红海第N条… / 张力依据在材料中不成立因为… / 市场不会买账因为…",
      "salvageable": true                                                  // 是否有可抢救内核(供重逼参考)
    }
  ]
}
```
- 三个 `kill_reason` 枚举**直接来自 C-P0 实测**(样本1杀"日照补偿交易"=撞红海;样本3杀"通高套利"=张力不实、杀"错位日照"=自嗨)——不是拍脑袋的分类。
- writer 侧失败原因同构:`{"passed": false, "missing": "site_gene | evidence_chain | …", "detail": "换成高铁项目仍成立,缺不可复制场地基因…"}`(C-P0 三次打回的 missing 都能归进:样本1/2 缺场地唯一性,样本3 缺证据链)。

## 三、writer/concept 二次重跑输入格式

**回②的 concept(重逼)输入 = 五件套:**
```
1. 项目材料(同首轮,认知脊椎已确认字段优先)
2. 红海清单(①的原产出,不重跑)
3. 已否决候选清单: [{candidate, kill_reason, detail}...]  ← 硬约束:不许复活、不许换皮
4. 幸存者(若有)+ its writer 失败原因: {missing, detail}  ← 重逼方向:补的就是这个缺口
5. 指令追加: "上一轮失败缺口是{missing}。本轮张力必须锚定材料中【只属于这块地】的条件
   (具体地名/数值/相邻物/时序),产出的 main idea 若换到任何同类项目仍成立即视为失败。"
```
**④的 writer 二次输入 = 三件套:** 幸存概念(本轮) + 上轮独占句 + 上轮 missing——要求"新句必须修复 missing,且不得弱于上轮"。

## 四、落库字段(最小 DDL,两表,不动现有表)

```sql
-- 锻造链主表(一次完整锻造=一行)
CREATE TABLE forge_chains(
  id INTEGER PRIMARY KEY, project_id INTEGER NOT NULL REFERENCES projects(id),
  status TEXT NOT NULL DEFAULT 'running',      -- running|passed|exhausted|aborted
  rounds INTEGER NOT NULL DEFAULT 1,           -- 已跑轮数
  redsea_json TEXT NOT NULL DEFAULT '',        -- ①产出(每链一次)
  final_idea TEXT NOT NULL DEFAULT '',         -- passed 时的独占句;exhausted 为空(不伪造)
  tokens_est INTEGER NOT NULL DEFAULT 0,       -- 累计token估算(承接T4-3成本口径,先估后精)
  cost_est_fen INTEGER NOT NULL DEFAULT 0,     -- 估算成本(分)
  created_at DATETIME NOT NULL, updated_at DATETIME NOT NULL);

-- 工位产出表(每工位每轮一行,append-only 审计轨——对齐 cognition_versions 范式)
CREATE TABLE forge_steps(
  id INTEGER PRIMARY KEY, chain_id INTEGER NOT NULL REFERENCES forge_chains(id) ON DELETE CASCADE,
  round INTEGER NOT NULL, step TEXT NOT NULL,  -- compete|concept|judge|writer
  status TEXT NOT NULL,                        -- ok|failed
  output_json TEXT NOT NULL DEFAULT '',        -- 结构化产出(judge=处决记录/writer=独占句+自检)
  fail_reason_json TEXT NOT NULL DEFAULT '',   -- §二的失败原因结构(回路输入源)
  model TEXT NOT NULL DEFAULT '', tokens_est INTEGER NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL);
```
- **通过** = chains.status='passed' + final_idea 非空;**打回** = 新一轮 steps 追加(旧轮保留,可追溯"逼"的全过程);**全灭** = 该轮 judge step 的 fail_reason_json 记全灭死因。
- 复用不新造:产出同时落一条 `skill_results`(现表)供营地成果列表展示,`source` 标 `forge`——两表是审计轨,skill_results 是展示口径,不冲突。

## 五、终止条件(硬门,防无限逼)

1. **通过即停**:writer 自检 passed → 链终态 passed。
2. **轮数上限:3 轮**(首轮+2次重逼)。C-P0 实测一轮约 1.2万 tok;3 轮封顶约 4万 tok。第 3 轮仍未过 → `exhausted`,**如实呈现最佳幸存者+未通过原因,不硬编独占句**(三态诚实在链里的体现)。
3. **全灭两连 → 提前 exhausted**:连续两轮 judge 全灭=材料撑不起非共识(C-P0 样本3 即此类),继续逼是烧钱,如实告知"该项目材料不足以锻造,建议补认知(指向③认知模块)"。
4. **人工中止**:任何时刻可 abort(状态可回溯,已花成本如实记)。

## 六、成本上限(承接 T4-3 成本口径,先行落地一小块)

- **单链预算:0.5 元**(estimate:3 轮×~1.2万tok×deepseek-chat 挂牌价≈0.11元,余量给 MoA-judge 模式);触顶 → aborted(reason=budget),**已花如实落库**。
- **judge 的 MoA 会诊模式(3 视角处决)为可选开关**,默认关(单 judge 已在 C-P0 证明敢杀);开 MoA 单链预算上调至 1.5 元,**开关设计上必须显式计费提示**(对齐 MinuteFlowCard"调用 DeepSeek·计费"范式)。
- 全局:锻造链调用计入 `forge_chains.tokens_est/cost_est_fen`——**这是 T4-3(MoA 成本黑箱)的第一块落地**:新功能从出生起就有账本,老功能的账本随 T4-3 方案单独批。

## 七、与数据基地 / 项目智能中心的关系

| 关系 | 口径 |
|---|---|
| **吃(输入)** | 材料走**现有 `gather_material` 三路取材**(已确认认知优先→解析文件→项目级检索)——锻造链是认知脊椎的重度消费者,**不新建取材管线**(一写新管线就停的铁律)。C-P0 实测教训:样本3(纯规范无项目语境)全灭——链的说明文案要写明"先入库项目材料、确认认知,再锻造"。 |
| **吐(输出)** | passed 的独占句+推导链 → 落 `skill_results`(营地成果卡展示)+ 可选回流 knowledge_documents(走现有 reflow 范式,人工确认后);**不自动写认知模块**(认知是人签字域,锻造产出只能"建议进入",对齐 draft→confirmed 纪律)。 |
| **不碰** | 检索/入库/解析/storage 全不动;蓝本 P0-P5 路权不占——锻造链后端=新增 2 表+1 router,不改任何现有心脏文件。 |
| **UI 归属** | 营地板内(改版方案§三锻造台),**本草案不含 UI 实施**——盲评赢了才谈。 |
