# 开发纪律 · 交付质量红线（2026-07-10 立，因"丑草稿重复端上来"事故）

> 本文件是工程铁律的一部分，进 git 仓库 = 换机器不丢 = 对后续所有会话生效（认知资产可移植性）。
> 触发本文件的事故：主控把用户**已明确叫停**的一批丑 HTML 小样，换了套 CSS 后**原封不动又做了一遍**端给用户；且这批页面与用户真正要做的功能并未对齐。这是"用低质量内容糊弄"+"反复要求没做到位"的复合失误。

---

## 铁律 1 · "叫停"叫停的是东西，不是表皮

用户否掉一个产出时，**否的是那个东西的本质（布局套路 / 交互形态 / 方向），不是它的某一层属性（配色 / 字体 / 命名）。**

- **禁止**：把"换个 CSS / 换个配色 / 换个措辞"当成"已按用户要求整改"。换皮 ≠ 整改。
- **必须**：叫停后，先问清楚"你否的到底是哪一层"——是方向不对？布局套路不对？还是根本不该做这个？**问清楚再动手，不许凭猜重做。**
- **反面教材（本次）**：用户否掉 5 个丑 HTML 小样，主控理解成"否的是那套灰配色"，于是用海天 token 重画一遍——**布局套路（暗色卡堆叠+居中弹窗+小灰字+emoji图标）原样保留**，等于把被否的东西又端了一遍。

## 铁律 2 · 一次犯错可以，同一个错不许犯第二次

同一类失误第二次出现，**性质从"失误"升级为"糊弄"**。

- 每当用户表达不满 / 叫停，**当场把"错在哪、以后怎么避免"追加到本文件**，后续执行先读本文件。
- 动手前自检：**"我这次做的，和上次被否的，是不是同一个东西？"** 若是——停，不许做，回去问用户。
- **反面教材（本次）**：删丑草稿的决议里已写"以后用真 seasky 组件做、不自创通用审美"，但主控随后仍产出同套路小样——**决议写了却没约束住自己的行为**。纪律必须在动手前被读、被执行，不是写完就忘。

## 铁律 3 · 不对齐需求，不许先画图

产出任何页面 / 小样 / 方案前，**先确认"这个板/这个功能，用户到底要解决什么问题、要什么形态"，再动手。**

- **禁止**：凭自己脑补的功能范围画图，然后拿"我以为你要这个"搪塞。
- **必须**：功能不清时，用一两个问题问清楚（要解决的核心问题 / 期望的交互 / 参照物），**得到答复再产出**。
- **反面教材（本次）**：4 个小样是主控按自己想象的功能画的，与用户真正要做的"几乎毫无关系"。

## 铁律 4 · 视觉产出的唯一合法路径 = 真组件，不是手写草稿

（承接 `前端补齐优先级-20260709.md` 的"手写 HTML 小样被否"裁决，升格为长期铁律）

- 要给用户看 UI 效果，**只能用现有 seasky 真组件（`GlassCard`/`PillButton`/`StatBlock`/海天 token）在真 React 代码里做**，`npm run build` 出 dist（8000）给用户看真效果。
- **禁止**手写独立 HTML 静态草稿来"演示交互/样子"——它们必然与真实组件脱节、且极易滑回通用审美（暗色卡+居中弹窗+emoji）。
- 唯一例外：用户**明确要求**要静态草稿时，只能复用用户认可过的那套海天 CSS，且**先说清这是草稿、非真实现**。

## 铁律 5 · "自评通过"不算数，交付前先自问三句

端给用户前，主控必须自问并能诚实回答：

1. **这是不是用户被否过的东西的变体？**（是→停）
2. **这和用户真正要做的对齐吗？**（不确定→先问，别端）
3. **视觉上，我自己看着觉得丑/像通用 AI 产物吗？**（是→不许端，说"我做不到位，需要重新对齐方向"）

宁可**如实说"这个我一时做不好、需要你先定方向"**，也不许**端一个自己都心虚的东西上来充数**。用户的时间不该花在反复否决低质量产出上。
