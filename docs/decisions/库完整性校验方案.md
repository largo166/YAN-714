## 一、核心:四态体检
按**真实落盘口径**核验每条 ProjectFile 的物理文件——口径就用这次踩坑摸清的:
- `storage_root` 非空 → 物理路径 = `storage_root / stored_path`(stored_path 为绝对则直接用);
- `storage_root` 空 → 回退 `DATA_DIR/uploads / stored_path`。

对每条记录判定,分四态出报告:
| 态 | 判定 | 含义 |
|---|---|---|
| ✅ 记录在·文件在 | 物理文件 exists | 健康 |
| ⚠️ 记录在·文件丢 | 记录有、物理文件不存在(但其 root 存在) | 零星文件丢失 |
| 🔵 文件在·记录无(孤儿) | 扫 storage_root/uploads 下有物理文件、但无对应活动记录 | 孤儿文件(入库中断/记录被删) |
| 🔴/🟡 **root 脱节(第四态,新增)** | 某 storage_root 目录不存在(🔴)或为空(🟡),而库里有指向它的存量记录 | 整个仓库根迁走/丢失(7-06 换根即此) |

**root 脱节两个子态(边界已拍,2026-07-07):**
- 🔴 **root 不存在** = 路径失效 = 事故。
- 🟡 **root 空置** = root 存在但为空。判定分两种:①**空置 + 该 root 下有存量记录** = 按脱节处理(文件该在而不在,标 🟡);②**空置 + 无记录** = 健康(新配的根待入库,正常,不报警)。

**第四态与零星丢失分开报**:root 脱节是**系统性**的(一次丢一整根),要一眼看出"仓库根迁走了",不淹没在成百条"文件丢"里。报告先按 storage_root 分组,每组先判 root 级(不存在/空置/正常),root 脱节则整组标 🔴/🟡 汇总"该根 N 条全受影响",不再逐条报 ⚠️(⚠️只用于 root 正常但个别文件丢)。
