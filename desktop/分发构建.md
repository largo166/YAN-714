# ROM-AI exe 分发构建(预置 key + WebView2 引导)

> 本文是「发 exe 给别人本地用」的操作手册。当前形态:单 exe 绿色版 + WebView2 方案 B(缺了联网自动装)。
> **T0-2 防呆(2026-07-08):默认 keyless。`.env.bundle` 在场也不会被打入——只有构建时显式设 `ROMAI_BUNDLE_KEY=1` 才打入。**

## 一、(可选)预置 key —— 显式开关制

1. 复制模板,填**分发专用** key(⚠️ 不要用主 key,详见模板内安全告知):
   ```
   cp desktop/.env.bundle.example desktop/.env.bundle
   # 编辑 desktop/.env.bundle,填 DEEPSEEK_API_KEY / IMAGE_API_KEY 等
   ```
2. `desktop/.env.bundle` 不入 git(`.gitignore` 的 `.env.*` 已忽略)。**它在不在场都不影响默认打包——默认永远 keyless。**
3. 要打**带 key 包**:构建命令前置 `ROMAI_BUNDLE_KEY=1`(PowerShell: `$env:ROMAI_BUNDLE_KEY="1"`)。spec 会在构建输出里大声宣告"本次打包内含预置 key";若设了开关但文件缺失,构建直接失败(防半配置)。

## 二、build

```powershell
cd "C:\ROM-AI-Claude 开发\frontend"; npm run build          # 出前端 dist
# keyless 包(默认):
cd "C:\ROM-AI-Claude 开发"; python -m PyInstaller desktop/romai.spec --noconfirm --distpath dist_exe --workpath build_exe
# 带预置 key 包(显式开关):
$env:ROMAI_BUNDLE_KEY="1"; python -m PyInstaller desktop/romai.spec --noconfirm --distpath dist_exe --workpath build_exe; Remove-Item Env:ROMAI_BUNDLE_KEY
# 产物:dist_exe\ROM-AI.exe
```

## 三、build 后必做冒烟(不依赖真机)

```powershell
# keyless 包(默认)——断言包内无 key,断言失败=有 key 泄进包,不许发:
pwsh desktop/smoke_test.ps1 -ExpectKeyless
# 带 key 包——断言预置 key 已注入:
pwsh desktop/smoke_test.ps1 -ExpectKey
```
全过 → exe 的「打包正确性 + 各板块接口不漏模块 + 空库自举 + key 形态与意图一致」已验证。

## 四、真机冒烟(L4/L5,smoke_test 覆盖不到,发出前在另一台/另一账户做一次)

- 双击 exe → 应弹 ROM-AI 窗口(WebView2 缺失会先联网装引导器;装不上弹提示框)。
- 走一遍五板块;关窗后任务管理器确认 ROM-AI 进程已退出。
- 填/确认 key 后真跑一条 AI 研判(验证联网 + key 有效)。

## 五、注入机制(排错参考)

| key | 落点 | 注入路径 |
|---|---|---|
| DeepSeek | DB `AppSetting.deepseek_api_key` | 首启空库 → `seed_if_empty` 读 `settings.deepseek_api_key` 写入(仅冻结态) |
| 生图/ASR | `%LOCALAPPDATA%\ROM-AI\.env` | 首启 `config._bootstrap_bundled_env` 把 `_MEIPASS\.env.bundle` 复制过去 |

- 只在 `DATA_DIR\.env` 不存在 / DB 为空时注入一次;用户后续改动不被覆盖。
- 关键日志:`%LOCALAPPDATA%\ROM-AI\launcher.log`(开窗/WebView2/后端就绪)。

## 六、已知边界(无法封装,需提前告知收件人)

- **要联网**:AI 调 api.deepseek.com / api.apimart.ai,公司网/代理/墙拦了即不可用。
- **预置 key 会泄露**:exe 可解包,key 随每个副本走 → 只发可信范围,用可吊销限额 key。
- **升级即炸库(未修)**:`init_db` 只 `create_all` 不跑 `alembic upgrade`。当前发**第一版**(收件人都是空库)无碍;一旦改了表结构再发**新版**给已装用户,会报 `no such column`。发 v2 前必补「启动 `alembic upgrade head` + DB 滚动备份」。详见第七节。

## 七、环境与迁移(开发环境 / 发新版必读)

### A0. 打包解释器口径(2026-07-08 OCR 进包起)

- **打包统一用 `backend/.venv/Scripts/python.exe`**(权威解释器,与测试同源)——系统 Python 没有 rapidocr,用它打包 OCR 必缺件。
- 命令改为:`backend/.venv/Scripts/python.exe -m PyInstaller desktop/romai.spec ...`
- OCR 进包(已批):rapidocr_onnxruntime + onnxruntime 收进 hiddenimports+collect_data_files(模型 ~15.5MB)。
  **体积账:113.0 MB(internal-0.2 无OCR) → 127.2 MB(+14.2 MB)**。收件人开箱即有图片/扫描件 OCR。

### A. 依赖完整性 —— 尤其 PyMuPDF(fitz)

- `requirements.txt` 列了 `PyMuPDF==1.26.5`,但 **Windows 上偶尔装失败**(本机 `backend/.venv` 就曾漏装),后果是**所有 PDF 解析 + PDF 抽图静默失败**(`parse_status=failed`,易被误判成"需 OCR")。
- 装完依赖**务必验**:`python -c "import fitz; print(fitz.version[0])"`。缺了 → `pip install PyMuPDF`。
- **exe 打包同理**:跑 PyInstaller 的那个 Python 必须有 fitz(`romai.spec` 的 hiddenimports 收的是 fitz),否则 exe 内 PDF 链路全废。打包前在该 Python 里也验一次 `import fitz`。

### B. 数据库迁移 —— create_all 不够,列变更必须 alembic upgrade

`init_db` 只 `Base.metadata.create_all`:能建**缺失的表**,但**不会给已有表加列**。所以:

| 变更类型 | create_all | 已有库 |
|---|---|---|
| 新增**表**(如 0015 skill_results、0017 file_assets) | ✅ 自动建 | 空库/新环境无碍 |
| 新增**列**(如 0016 analysis、**0018 project_files.content_chunks_json**) | ❌ 不加 | 会 `no such column`,**必须 `alembic upgrade head`** |

当前 head:`0018_project_file_chunks`。对**已有库**升级(迁移均带幂等守卫,可安全重复跑):

```powershell
cd backend; python -m alembic upgrade head
```

### C. 发新版 exe 给已装用户(v2+)的红线

- 收件人 DB 在 `%LOCALAPPDATA%\ROM-AI\rom_ai.db`,是**老结构**。
- 新版 exe 若含**列变更**迁移(如 0018),光靠 create_all 不加列 → 启动后用到该列即炸(`no such column: content_chunks_json`)。
- 发 v2 前必须:① **让 exe 启动跑 `alembic upgrade head`**(目前 launcher/init_db 未接,需补)② DB 滚动备份(G2)。
- 第一版(收件人空库)不受影响——create_all 会按最新模型一次建全。
